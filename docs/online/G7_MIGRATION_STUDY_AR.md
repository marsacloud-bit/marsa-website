# دراسة ترحيل البيانات القديمة — مرسى، G7 الخطوة ١٠

> **الحالة: دراسة وقوالب فقط.** الترحيل **اختياري** ولا يعطل التجربة ببيانات جديدة (نص الخطة). لا يوجد في G7 أي RPC استيراد جديد (G7-17). كل بنود الجرد والتنظيف والقرار وتجربة الاستيراد `قيد انتظار المالك (OWNER-PENDING)`.
> القوالب: [`../import-templates/README_AR.md`](../import-templates/README_AR.md) (`clients`، `transactions`، `containers` بصيغتي CSV وxlsx).

## 2) ما يُرحَّل وما لا يُرحَّل

| يُرحَّل (عند الموافقة) | لا يُرحَّل أبدًا |
|---|---|
| ملفات العملاء النشطة (السجل الرئيسي) | كلمات المرور وبيانات الدخول لأي نظام |
| المعاملات **المفتوحة** فقط، كطلبات عبر الرفع الجماعي | بيانات البطاقات والحسابات البنكية |
| أرقام الحاويات ومواعيد الإرجاع للمعاملات المفتوحة | أرقام الهويات الكاملة (السائق: آخر 4 أرقام فقط) |
| — | الرسائل القديمة (بريد / واتساب) دون موافقة موثقة من أطرافها |
| — | الفواتير الرسمية الصادرة (مصدرها دفترة) |
| — | حالة «أُرجعت» القديمة كإثبات (يلزم إيصال على المعاملة) |
| — | المعاملات المغلقة التاريخية (تبقى في النظام القديم للمرجع، ما لم يقرر المالك غير ذلك) |

## 3) قواعد جودة البيانات

| القاعدة | التحقق | المعالجة |
|---|---|---|
| تكرار العملاء | مطابقة بالرقم الضريبي ثم السجل التجاري ثم الاسم بعد التوحيد العربي | سجل رئيسي واحد لكل عميل؛ الأسماء الأخرى تُضاف «أسماء بديلة» يدويًا بعد الترحيل |
| الرقم الضريبي | 15 رقمًا؛ السعودي يبدأ وينتهي بـ 3 (`^[0-9]{15}$` في القاعدة) | يُترك فارغًا إن كان غير صالح، ويُسجَّل في ملاحظات التنظيف |
| السجل التجاري | 10 أرقام (`^[0-9]{10}$`) | كما سبق |
| الجوال | `0` ثم 9 أرقام (`^0[0-9]{9}$`)؛ `+966` يُحوَّل إلى `0` | كما سبق |
| أرقام الحاويات | ISO 6346: 4 أحرف + 7 أرقام **وخانة تحقق صحيحة**؛ رقم واحد مرة واحدة في المعاملة نفسها (يجوز في معاملات مختلفة كزيارات منفصلة) | تصحيح الأخطاء الشائعة (O↔0، مسافات، شرطات)؛ رفض ما تبقى غير صالح |
| التواريخ | `YYYY-MM-DD` بتوقيت الرياض؛ لا تواريخ هجرية (غير مدعومة) | تحويل الهجري إلى ميلادي قبل الاستيراد |
| التوحيد العربي | إزالة التشكيل والتطويل، توحيد الهمزات (أ إ آ ← ا)، ى ← ي، ة ← ه للمطابقة فقط | يُخزَّن الاسم كما هو؛ التوحيد للمقارنة |
| المنافذ | من قائمة منافذ الموقع (مثل «ميناء جدة الإسلامي») | مطابقة يدوية للأسماء القديمة |
| العملات | USD أو EUR أو CNY أو AED أو SAR (حدود الرفع الجماعي) | غيرها يحتاج قرارًا |
| النصوص | حدود الطول في القاعدة (مثل وصف البضاعة ≤ 1000) | اقتطاع مع ملاحظة |

## 4) المطابقة مع جداول مرسى

| المصدر | الوجهة | المسار اليوم |
|---|---|---|
| العميل | `public.clients` (+ `client_aliases`) | يدوي: «العملاء ← عميل جديد»، أو عند «تحويل إلى معاملة» |
| الشحنة / المعاملة | `public.service_requests` (`source='bulk'`) ← `public.transactions` | `bulk-upload.html` (نوع «شحنات») ← `import_commit` ← مراجعة ← `convert_request_to_transaction` |
| رقم البوليصة | `bills_of_lading` + `transaction_bls` | من حقل «رقم البوليصة» في الطلب، ثم قسم «بوالص الشحن» |
| الحاوية | `public.containers` | أرقام من حقل «أرقام الحاويات»، أو «إضافة حاوية» يدويًا؛ التفاصيل (الختم، الوزن، مواعيد الإرجاع) يدويًا من «تحديث» |
| مواعيد الإرجاع | `containers.return_deadline` | يدويًا من «إرجاع الحاويات الفارغة» |
| المستندات | `documents` + Storage | رفع يدوي على المعاملة ثم تصنيف |
| فواتير الموردين المفتوحة | `finance_documents` + بنود | يدوي من «فواتير الموردين» (مع الأصل) |

ملاحظة: ترقيم مرسى (`REQ-…` و`<prefix>-YYYY-NNNNNN`) يُولَّد على الخادم؛ **لا يُحفظ المرجع القديم كرقم مرسى**. الربط بين القديم والجديد يكون بجدول مطابقة خارجي (§5).

## 5) خطوات التنظيف والمطابقة العددية

1. استخراج كل مصدر إلى القالب المناسب (نسخة عمل خارج المستودع، على جهاز الشركة فقط).
2. تطبيق قواعد §3 وتسجيل كل تعديل في ورقة «سجل التنظيف» (السطر، الحقل، القيمة قبل، بعد، السبب).
3. إزالة التكرار وإنتاج قائمة العملاء الرئيسية.
4. **مطابقة عددية قبل الاستيراد:**

| المقياس | في المصدر | بعد التنظيف | مستبعد (مع السبب) |
|---|---|---|---|
| عدد العملاء | | | |
| عدد المعاملات المفتوحة | | | |
| عدد الحاويات | | | |
| مجموع أعداد الحاويات لكل معاملة | | | |

5. **مطابقة عددية بعد الاستيراد** (في المؤسسة التجريبية): عدد صفوف الدفعة المعتمدة = عدد الطلبات المنشأة (`import_commit`: `committed`)، والمكررة والأخطاء مسجّلة على الصفوف؛ ملف «المراجع» من الرفع الجماعي (`marsa-refs-<batch>.csv`) يربط رقم الصف برقم الطلب، ويُضم إلى جدول المطابقة (رقم الصف ← المرجع القديم).
6. عينة عشوائية (10 سجلات على الأقل) يراجعها موظف يقارن القديم بالجديد حقلًا بحقل.

## 6) إجراء تجربة الاستيراد المحدودة (G7-17) — OWNER-PENDING

شروط مسبقة: موافقة المالك المكتوبة على (أ) المصادر، (ب) عدد السجلات (مقترح ≤ 50 معاملة مفتوحة)، (ج) هل البيانات حقيقية (تخضع لمراجعة الخصوصية في `G7_READINESS_REVIEW_AR.md` §8) أم مموّهة.

1. نسخة احتياطية من Staging.
2. إنشاء **مؤسسة تجريبية منفصلة (sandbox)** من «لوحة المنصة» (مثل المعرّف `org-migration-trial`)؛ لا يُستورد إلى مؤسسة البحر الأزرق التجريبية الرئيسية.
3. إنشاء العملاء يدويًا (أو تركهم للإنشاء عند التحويل بعد مراجعة المطابقات).
4. رفع `transactions.xlsx` المعبأ عبر «الرفع الجماعي» ← مراجعة الأخطاء والتحذيرات ← رفع واعتماد.
5. مراجعة «الطلبات الواردة» وتحويل عينة إلى معاملات، ونقل مراحلها يدويًا حسب الحالة الحقيقية (قواعد المستندات تنطبق).
6. المطابقة العددية §5 بند 5، وتسجيل النتائج.
7. قرار المالك: ترحيل كامل، أو جزئي، أو بدء جديد بلا ترحيل.
8. بعد التجربة: تعليق المؤسسة التجريبية («تعليق» بسبب «انتهاء تجربة الترحيل»)؛ لا حذف (لا مسار حذف في النظام).

## 7) المخاطر

| الخطر | الأثر | التخفيف |
|---|---|---|
| تكرار عملاء بأسماء مختلفة | معاملات موزعة على ملفات متعددة | المطابقة بالأرقام أولًا + مراجعة بشرية |
| أرقام حاويات خاطئة | تنبيهات إرجاع خاطئة | التحقق بخانة ISO 6346 |
| ترحيل حالة «أُرجعت» بلا إيصال | ادعاء إرجاع بلا إثبات | لا تُنقل الحالة؛ تبدأ «بانتظار الإرجاع» |
| حجم عمل التحويل اليدوي | وقت موظفين | ترحيل المعاملات المفتوحة فقط؛ القديمة تبقى في النظام السابق |
| بيانات حقيقية على Staging | مخاطر خصوصية | موافقة مكتوبة + مراجعة PDPL + مؤسسة sandbox |
| حدود الباقة | رفض إنشاء معاملات | المؤسسة التجريبية على باقة `pilot` (بلا حدود) |
